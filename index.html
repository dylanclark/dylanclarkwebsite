Hi, I'm Dylan Clark. I'm a Principal Software Engineer at Microsoft, based in Cambridge, MA. I build backend services, shared frameworks, and developer tools. I like taking a problem that isn't quite figured out yet and getting something useful into people's hands.

What I'm building

I build services for agentic Outlook experiences, taking them from an idea to worldwide deployment. As I build, I develop tooling and focus on capacity, monitoring, and evaluations to make sure the software works well as it grows. I like carrying an idea through that whole process, including the work it takes to make it dependable in production.

AI is also part of how I build. I develop tools and agentic workflows with a focus on developer experience and reliability, including automating the generation of compliance artifacts. I like finding the repeated friction in a team's day and building something that gets it out of the way.

How I got here

I joined Microsoft after graduating from Harvard in 2018 and started in desktop Outlook, working in C++. Since then, I've helped build a shared WebView2 application hosting framework used by Outlook, Copilot, OneDrive, and other Microsoft products. That meant designing APIs and writing code, working directly with adopting teams, and making it easier for them to debug and contribute improvements.

Some of the most useful work has meant getting into someone else's system. When an Outlook integration depended on a service with missing technical context, I learned the codebase, tracked down its history, and worked with the owning team to implement the changes. I've also spent years on the work that keeps releases dependable: build systems, staged rollouts, telemetry, and figuring out why an update didn't do what we expected.

How I work

I'm a generalist with a particular fondness for backends, frameworks, and developer tools. Give me a fuzzy problem, a few people with different priorities, and something useful to build, and I'm happy. I like getting enough context to make a decision, testing the risky assumptions, and getting a first version into people's hands so we can learn from it.

Sometimes that means leading a cross-team effort; sometimes it means pairing with someone or digging into an unfamiliar service myself. I care about being a patient, useful teammate. Mentoring engineers and helping them take ownership of bigger problems has become one of my favorite parts of the job.

Tools and interests
  • C#/.NET and modern C++; TypeScript, React, and Python when the work takes me there
  • MCP, coding agents, and developer experience for AI
  • Azure services, Docker, Kubernetes-based infrastructure, and infrastructure as code
  • CMake, Azure DevOps, GitHub Actions, and all the other fun tools that get thrown together to ship code
  • APIs people can understand, useful telemetry, and systems that someone besides the author can maintain

I'm especially curious about applying AI to science and to the everyday work that still involves too much friction. If you're building something interesting, I'd love to hear about it.
